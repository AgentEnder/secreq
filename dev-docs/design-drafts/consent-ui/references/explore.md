# Exploration: secreq consent UI restyle

> Generated by `design-drafts:explore` on 2026-07-09. Working document — `design-drafts:brief` reads this to seed its interview. Concepts are PROPOSED, not committed; the brief is where they get pinned down.

## Premise

"It should feel like a desktop app, and look like a desktop app, not like an AI-designed web app." The user is "just not **super** happy with the current UI, it looks super LLM and is a bit less sleek than I'd prefer." Drafts are designed as web views but will be adapted to Rust (egui) UI elements during implementation.

Diagnosis of the current UI agreed on during the session (what "looks super LLM" means concretely): GitHub-dark ground + blue accent + rounded 1px-bordered cards (anti-pattern #2 family); filled green/red pill button pairs repeated at three tree levels (#7); colored status pills (`approved •`, `2 pending •`); rounded search bar with keyboard-shortcut chip.

## Axes under consideration

For each axis discussed: candidate concepts the user reacted to. Concepts marked `[picked]` should carry into the brief.

### theme

- **Terminal Ledger** [picked] — the daemon's window looks like a first-class TUI that happens to have a titlebar: monospace everywhere, no cards, no borders, rows aligned to a strict column grid separated by whitespace and hairline rules, one amber accent for pending state.
  - keywords: k9s, htop, ledger paper, phosphor
  - pushes against: #2 (glow-and-blur dark mode), #7 (pill buttons) — no filled buttons, only bracketed keyboard affordances like `[a]pprove`
- **Native Sentinel** [picked] — leans into being an OS security surface rather than an app: system-neutral grays, minimal corner rounding, real OS-weight button affordances, compact window that reads as kin to the macOS Keychain prompt or 1Password unlock — unashamedly a dialog, not a dashboard.
  - keywords: Keychain, UAC done tastefully, NeXT, "part of the OS"
  - pushes against: "web app wearing a desktop window costume" — which is arguably what the current UI is
- **Security Paper** — light theme; consent as paperwork: paper-white ground, ink-dark type, hairline rules like a bank slip, decisions rendered as overprint stamps, mono reserved strictly for commands.
  - keywords: receipts, letterpress, security-printing guilloche, notary
  - pushes against: dark-by-default, colored status pills — a stamp is a record, a pill is a label
- **Flight Deck** — dark but instrument-grade instead of startup-sleek: flat panels stepped by luminance, small-caps microlabels, tabular numerals, signal color demoted to thin 2px rails and ticks.
  - keywords: avionics, Braun/Rams, mission control, restraint
  - pushes against: #2, and the traffic-light filled-button pair — color as indicator, never as surface

### density

- **Manifest Rows** [picked] — one line per ask, Activity-Monitor style: real columns (command / secrets / age), disclosure triangles for the process tree, full detail in a pane below or on expand; nothing is a card, everything is a row.
  - keywords: NSTableView, Activity Monitor, Finder list view
  - pushes against: card-per-item — the single most webby structure in the current UI
- **Grouped Inset** [picked] — close to today's structure but translated to the macOS System Settings idiom: grouped inset blocks with hairline separators inside, not free-floating rounded cards with borders.
  - keywords: System Settings, grouped lists, inset
  - pushes against: cards floating on a void
- **Focus Stack** [picked] — one ask at a time, rendered big like a 1Password unlock or UAC prompt; the queue is just "2 more waiting" text; the window is a prompt, not a browsing surface.
  - keywords: 1Password, UAC, one-decision-at-a-time
  - pushes against: dashboard-ness entirely — you don't browse pending asks, you answer them

### decision-surface

- **Dialog Buttons** [picked] — real OS-weight push buttons, right-aligned like a native alert: Deny plain, Approve as the single default-highlighted action, Enter/Esc semantics, exactly one button pair visible at a time (the selected scope).
  - keywords: NSAlert, default button, restraint
  - pushes against: #7 — six green/red pills visible at once in today's tree
- **Keyboard-First** [picked] — controls are nearly invisible: select a row, hit A or D; hints shown as key glyphs, buttons materialize only on hover; the Terminal Ledger's natural partner.
  - keywords: Mail j/k, vim, k9s
  - pushes against: button-driven UI at all
- **Asymmetric Friction** [picked] — deny is one instant click; approve requires a beat more (hold-to-confirm or click-then-confirm); the UI physically encodes that granting a secret is the dangerous direction.
  - keywords: hold-to-confirm, dead-man switch, safety interlock
  - pushes against: approve and deny styled as equal-weight twins

### layout

- **Master-Detail Split** [picked] — sidebar (Pending / Rules / Audit) + detail pane; the classic document-app skeleton.
  - keywords: Mail, Keychain Access, sidebar
  - pushes against: web-app top tabs
- **Top Tabs, Tightened** [picked] — keep today's tab bar but make it native-weight (segmented control or toolbar tabs), since three sections may not earn a sidebar.
  - keywords: segmented control, toolbar
  - pushes against: nothing structural — this is the "the bones were fine, the skin was the problem" position
- **Prompt + Manager** [picked] — split the app in two: consent is a small transient panel (menu-bar-extra style, appears, answers, gone), while Rules and Audit live in a separate manager window opened deliberately.
  - keywords: menu bar extra, Little Snitch's prompt vs. its rule editor
  - pushes against: one-window-does-everything — arguably the deepest reason the current UI feels like a web app

## Open threads

- Theme: one hybrid direction or two separate theme choices in the variants grid? (Terminal Ledger vs. Native Sentinel, or a fused "mono content in native chrome" stance.)
- Density, decision-surface, and layout each carry all three options — the user deferred elimination to the brief. The brief must force picks; four axes × 3 choices is far too big a grid to build honestly.
- Whether four axes should collapse to three or fewer before variants (e.g. decision-surface may be implied by the theme pick: Terminal Ledger → Keyboard-First, Native Sentinel → Dialog Buttons).
- Prompt + Manager layout implies a two-window architecture (transient consent panel + separate manager window) — a real change to the daemon's UI structure, not just styling. If it wins, the design plan at `dev-docs/plans/2026-06-02-auto-rules.md` and the screenshot-fixture harness both need to reflect it.
- How far egui can go toward "native-weight" chrome (real default-button styling, segmented controls, menu-bar-extra behavior) — implementation constraint to check before the brief promises it.
- Light theme is currently entirely off the table (Security Paper was walked away from). Confirm in the brief that dark-only is intentional for a consent prompt that pops over arbitrary desktops.
